3.1 Inside the back end: a Python web server 12 min

Here is a complete dynamic web server written in Python, using a popular framework called Flask. It is short enough to read in full.

from flask import Flask
from datetime import datetime

app = Flask(__name__)

@app.route("/")
def home():
    return "<h1>Rosenthal's Bakery</h1><p>Fresh bread every morning.</p>"

@app.route("/hours")
def hours():
    now = datetime.now()
    if 7 <= now.hour < 18:
        return "<p>We are <b>open</b> right now!</p>"
    return "<p>We are closed. Back at 7 a.m.</p>"

app.run(port=5000)

Walk through it slowly with the class:

  • app = Flask(__name__) creates the web server program. Flask is a framework (Session 1): a bundle of pre-written code that handles the routine parts of being a web server, so the developer only writes the parts unique to the bakery. Flask, Django, and FastAPI are Python frameworks; Express and Next.js are JavaScript ones; Rails is Ruby; Spring is Java. When Claude Code builds you a web app, it will pick one of these.
  • Each @app.route("...") line is a route: it connects a path (the part of the URL after the domain) to a Python function. When a request for /hours arrives, the hours() function runs and whatever it returns is sent back as the response.
  • The hours() function is where "dynamic" happens. It checks the current time and returns different HTML depending on the answer. Two visitors a minute apart at 5:59 p.m. and 6:00 p.m. see different pages. No static file could do that.
  • app.run(port=5000) starts listening. A port is a numbered door on a computer. One machine can run many server programs, each behind a different door. Websites use port 443 (HTTPS) and 80 (HTTP) by convention, so you never type them; developers testing on their own machine use doors like 5000 or 3000, which is why you will see addresses like http://localhost:5000.

localhost means "this computer." When you run the program above and open http://localhost:5000/hours, your browser is the client, your own laptop is the server, and the request never leaves the machine. Every developer works this way before putting anything on the internet. Session 4 covers the jump from localhost to the world.

Live demo (4 minutes)
  1. Ask Claude Code to create the Flask app above and run it.
  2. Open http://localhost:5000 and http://localhost:5000/hours in a browser.
  3. Change the closing hour in the code, save, refresh. Point out that the HTML did not exist as a file anywhere; the program composed it on demand.
  4. Try http://localhost:5000/nothing to get a live 404.

In practice, back ends do not build HTML by gluing strings together. They use templates: HTML files with blanks in them, such as Welcome back, {{ customer_name }}, which the program fills in for each request. Designers can edit the template without touching the Python, and the Python can change without touching the design. The idea to carry away is the same either way: the server runs code, and the code produces the page.

3.2 APIs and JSON: how programs talk to programs 15 min

The Flask example returned HTML for a human to read. But increasingly the thing making the request is not a human's browser rendering a page. It is another program: JavaScript in the page asking for "just the data," a mobile app, a partner's system, or an AI assistant. For those callers, the server returns raw data instead of a designed page. The set of requests a server understands, and the shape of the answers it gives, is its API (Application Programming Interface).

Analogy

Back to the restaurant. The menu is the API. It lists exactly what you may order and what you will get. You do not need to see the kitchen, and the kitchen can be reorganised without changing the menu. A menu written in a standard format lets anyone order, including delivery apps that were never imagined when the restaurant opened.

A web API is reached over HTTP just like a page, but its endpoints (individual addresses) return data rather than HTML. Here is the bakery adding one:

@app.route("/api/products")
def list_products():
    return {
        "products": [
            {"id": 1, "name": "Sourdough loaf", "price": 7.50, "in_stock": True},
            {"id": 2, "name": "Rye bread",      "price": 6.00, "in_stock": False},
            {"id": 3, "name": "Challah",        "price": 8.00, "in_stock": True}
        ]
    }

A request to /api/products gets back this:

{
  "products": [
    {"id": 1, "name": "Sourdough loaf", "price": 7.5, "in_stock": true},
    {"id": 2, "name": "Rye bread", "price": 6.0, "in_stock": false},
    {"id": 3, "name": "Challah", "price": 8.0, "in_stock": true}
  ]
}

This format is JSON (JavaScript Object Notation, pronounced "Jason"). Curly braces hold a set of named values; square brackets hold a list; text is in quotes; numbers and true/false stand alone. Python students will recognise it: a JSON object is almost exactly a Python dictionary, and a JSON array is a Python list. Every programming language can read and write JSON, which is why it became the common tongue of the web.

Verbs: GET, POST, and friends

HTTP requests carry a method, a verb stating the kind of action. Static sites only ever needed GET ("give me this"). APIs use the full set:

MethodMeaningBakery exampleBusiness action
GETRead; fetch somethingGET /api/productsShow the catalogue
POSTCreate; submit new dataPOST /api/orders with the order in the bodyPlace an order
PUT / PATCHUpdate something existingPATCH /api/orders/88 with {"status": "ready"}Mark an order ready
DELETERemoveDELETE /api/orders/88Cancel an order

An API organised this way, where every URL names a thing (a product, an order) and the method says what to do to it, is called REST (or "RESTful"). Almost every API you will encounter, from Stripe to Shopify to the Claude API, is roughly REST. The letters stand for something (Representational State Transfer) that nobody needs to remember; the idea is nouns in the URL, verbs in the method.

The four verbs map to the four things any system does with data, remembered by the acronym CRUD: Create, Read, Update, Delete. A surprising fraction of all business software is CRUD screens over a database: customers, invoices, tickets, inventory. Recognising a product as "mostly CRUD" is a useful signal that it is well understood and inexpensive to build.

Who calls APIs?

The right-hand side of this picture is where much of modern product-building happens. A third-party API lets you rent a capability instead of building it: charge a card with Stripe, send a text message with Twilio, look up an address with Google Maps, or generate text with the Claude API. Each is usually billed per use, which turns what used to be an engineering project into a line item. Much of "using AI to build products" is, architecturally, calling the right third-party APIs from your back end.

Instructor note

Students will meet the phrase "API key" constantly. It is a long secret string a third party gives you that identifies your account when your back end calls their API, so they know whom to bill. It lives on your server, never in front-end code. We return to this in Session 5, but planting it here pays off.

3.3 Why every product needs a database 10 min

The /api/products example had its data typed directly into the program. That breaks the moment a real business touches it: the baker cannot edit Python to change a price, and an order placed by a customer has nowhere to be saved. The server needs somewhere to store data that survives restarts, can be changed by the program, and can be searched. That somewhere is a database.

Why not just save to a file, the way you might save a spreadsheet? Because a database solves problems a file cannot:

  • Many writers at once. Two customers buying the last challah at the same instant must not both succeed. A database handles this; a file being edited by two programs simultaneously gets corrupted.
  • Speed at scale. Finding one order among ten million by scanning a file takes minutes. A database with an index (like the index in a textbook) does it in milliseconds.
  • Reliability. If the power fails halfway through saving an order, a database guarantees the order is either fully saved or not saved at all, never half. This property is called a transaction. Moving money between two bank accounts is the classic case: the debit and the credit must both happen or neither.
  • Questions. "Which customers ordered rye more than three times last quarter?" is one line in a database language and a small programming project against a pile of files.

The database is a separate program, a database management system (DBMS). Your Python back end does not store data itself; it sends instructions to the DBMS and gets results back, much as the browser sends requests to the web server. In Session 4 we will see that the DBMS often runs on its own machine.

The relational model: tables

The dominant way to organise business data for the last fifty years is the relational model. Data lives in tables: each table holds one kind of thing, each row is one instance of that thing, and each column is one fact about it. The bakery needs at least these:

Two ideas make this work:

  • Every row has a primary key, a column whose value is unique for that row and never changes: customer_id, product_id, order_id. Names are not good keys because two customers can share one and people change theirs.
  • Instead of copying Dana's name and email into every order she places, the order stores only her customer_id. A column that holds the primary key of a row in another table is a foreign key. The orders table has two: customer_id and product_id. This is what "relational" refers to: tables related through keys.

The overall design of the tables, their columns, and the keys that link them is the schema. Designing a schema is really designing the business: what things exist, what we record about them, and how they relate. Business students are often better at this than engineers, because it is a question about the domain rather than about code.

3.4 SQL by example 15 min

Relational databases are all controlled with one language, SQL (Structured Query Language, said "sequel" or "S-Q-L"). It was designed in the 1970s to be readable by business analysts, and it largely is. You are not expected to write SQL in this course; you are expected to recognise it, read simple statements, and know what it can do. Claude Code will write the SQL, but you will be reviewing what it writes and asking for the right things.

A request to a database is a query. Six examples cover most of what a business ever needs.

Reading: SELECT

SELECT name, email FROM customers WHERE city = 'Boston';

"Give me the name and email of every customer whose city is Boston." SELECT picks the columns, FROM picks the table, WHERE filters the rows. Result: Dana Levi and Priya Nair. Replace the column list with * to get every column.

Counting and summing: aggregate functions

SELECT status, COUNT(*) AS how_many
FROM orders
GROUP BY status;

"For each order status, how many orders are there?" Result: one row per status (placed 1, baking 1, ready 1). SUM, AVG, MIN, and MAX work the same way; together with COUNT they are called aggregate functions, because each combines many rows into a single number. Every management dashboard in the world is a stack of queries like this.

Combining tables: JOIN

SELECT customers.name, products.name, orders.quantity
FROM orders
JOIN customers ON orders.customer_id = customers.customer_id
JOIN products  ON orders.product_id  = products.product_id
WHERE orders.status = 'placed';

This is the query that makes the relational model pay off. The orders table has only ID numbers; a JOIN stitches each order to the matching customer row and product row using the keys, so the result reads like a human wants it to: "Dana Levi, Rye bread, 1." Whenever you see a report that combines information from several places, there is a JOIN behind it.

Writing: INSERT, UPDATE, DELETE

INSERT INTO orders (customer_id, product_id, quantity, status)
VALUES (3, 1, 2, 'placed');

UPDATE orders SET status = 'ready' WHERE order_id = 88;

DELETE FROM orders WHERE order_id = 89;
