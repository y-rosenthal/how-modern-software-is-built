Hosting, Scaling, and the Cloud

So far everything has run on one laptop. This session moves the bakery onto the internet and then grows it, one step at a time, from a single rented server to the distributed architecture used by companies serving millions of people. Each step is motivated by a specific problem the previous step could not solve, and each step has a price tag.

4.1 From localhost to production 10 min

The bakery's back end works beautifully at http://localhost:5000. Moving it to a place where customers can reach it is called deployment. "Deploy" is one of the most frequently used verbs in a software team, and it means exactly this: take the code that works here and make it run there.

Serious teams do not deploy straight from a laptop to customers. Code passes through environments, each a full copy of the application with its own database:

EnvironmentWho uses itPurposeData
Development ("dev", "local")Each programmer, on their own computerWrite and try code freely; break thingsFake or sample data
Staging ("test", "QA")The team, testers, sometimes the clientA private replica of production to check a release before customers see itRealistic but not real (or anonymised)
Production ("prod", "live")Real customersThe actual businessReal; protected and backed up

"It works on my machine" is the oldest joke in software precisely because development and production differ: different operating system, different database size, different traffic, different secrets. Staging exists to catch those differences before a customer does. When a founder asks "can we just push it live?" the honest engineering answer is "only if you would be comfortable finding the bugs at the same moment your customers do."

Two measures describe how well a production system is doing. Uptime is the percentage of time it is reachable; each extra "nine" is dramatically more expensive to achieve. Latency is how long each request takes to answer. Much of the architecture in this session exists to push uptime up and latency down.

UptimeDowntime allowed per yearTypical of
99%About 3.7 daysA hobby site on one cheap server
99.9% ("three nines")About 8.8 hoursA small business product with sensible hosting
99.99% ("four nines")About 53 minutesPayment, banking, large SaaS. Requires redundancy at every layer
99.999% ("five nines")About 5 minutesTelecom, critical infrastructure. Very expensive

4.2 Step 1: everything on one server 10 min

The simplest deployment is to rent one computer in a data center and install everything on it. Cloud companies rent these by the hour or month as virtual private servers (VPS) from providers such as DigitalOcean, Linode, Hetzner, or Amazon's EC2, for as little as 5 dollars a month. "Virtual" because one powerful physical machine is carved into several independent virtual ones, each of which feels to its renter like a whole computer.

On that one machine you install:

  • An operating system, almost always Linux on servers. Linux is free, stable, and what nearly all server software is built for. Windows and macOS run desktops; iOS and Android run phones; Linux runs the internet.
  • The web server program (Nginx is the usual choice), which accepts connections on ports 80 and 443, handles HTTPS, serves the static files itself, and forwards dynamic requests to the back end.
  • Your back-end program (the Python/Flask app), listening on an internal port such as 5000.
  • The database (PostgreSQL), listening on its own internal port, 5432 by convention.

Do not underestimate this setup. A modest 20-dollar server can comfortably handle tens of thousands of visits a day, which covers most small businesses and every early-stage prototype. Its weaknesses only appear with growth:

  • Single point of failure. If the machine's disk dies, or the data center loses power, or you make a mistake while updating it, the website and the database disappear together. A single point of failure is the enemy of uptime.
  • Resource contention. The database and the back end compete for the same memory and processor. A heavy report query can make the website slow for every visitor.
  • Hard ceiling. When traffic outgrows the machine, the only option is a bigger machine, and machines do not get infinitely big.
  • Security blast radius. If an attacker breaks into the web server, they are already sitting on the same machine as all the customer data.

Each of the following steps removes one of these weaknesses, and each adds cost and complexity. Good architecture means taking the next step when the problem is real, not before.

4.3 Step 2: give the database its own machine 10 min

The first thing to move off the shared server is the database. It goes onto a second machine, a dedicated database server, and the back end connects to it over the network instead of talking to it on the same box.

Why this is worth the second bill:

  • Right-sized hardware. Databases want lots of memory and fast disks; web servers want processor cores and network bandwidth. Separated, each can be bought for what it actually needs.
  • Security. The database server gets a private network address only. There is no route from the internet to it. A firewall allows connections on port 5432 only from the web server. An attacker who compromises the web server still has another wall to get through, and no one can stumble across the customer records from outside.
  • Independent failure and maintenance. The web server can be rebuilt, upgraded, or replaced without touching a byte of data. Backups of the database run without slowing the website.
  • It unlocks the next step. With the data in one shared place, you can now run more than one copy of the web server, which is what Step 3 does.

In practice, almost nobody installs PostgreSQL on a rented machine themselves any more. Cloud providers offer a managed database, such as Amazon RDS, Google Cloud SQL, Supabase, or Neon: you click "create PostgreSQL," and they run the machine, take nightly backups, install security patches, and can switch to a standby copy automatically if the primary fails. You get a connection address and a bill, starting around 15 to 50 dollars a month. For nearly every business this is the correct choice; running your own database is expertise you do not want to have to hire.
