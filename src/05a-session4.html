Identity, Security, and Software Beyond the Browser

Every architecture so far has quietly assumed the server knows who is asking. This session explains how it finds out: passwords, cookies and sessions, Basic Auth, and OAuth, the mechanism behind every "Sign in with Google" button. We then widen the lens from websites to phone apps, installed programs, and embedded devices, and finish with where AI services fit in the picture.

By the end of this session students can

  • Distinguish authentication from authorization with examples.
  • Explain why passwords are hashed and what multi-factor authentication adds.
  • Describe how a cookie keeps a user logged in across stateless requests.
  • Explain HTTP Basic Authentication and why it is only acceptable over HTTPS.
  • Walk through the OAuth authorization-code flow and explain what it protects.
  • Compare web, native mobile, cross-platform, desktop, and embedded software and describe how all of them use the same back end.
  • Explain where an AI model such as Claude sits in a product's architecture.

4.1 Authentication versus authorization 8 min

Two words that sound alike and are constantly confused, even by professionals. Keep them apart with two questions.

  • Authentication answers "Who are you?" It is the act of proving identity: a password, a code from your phone, a fingerprint, or a login through Google. Shortened to "authn" or just "auth".
  • Authorization answers "What are you allowed to do?" Once the system knows you are Dana, may Dana see order 90? May Dana see Sam's order 88? May Dana issue a refund? Shortened to "authz".
Analogy

An office building. Showing your badge at the front desk is authentication: they confirm you are an employee. Which doors your badge opens is authorization: the server room is not among them unless you are in IT. A guest badge authenticates you as a visitor and authorizes almost nothing.

Authorization is usually organised through roles: customer, staff, manager, administrator. Rules are written per role ("staff may mark orders ready; only managers may refund") and users are assigned roles. Deciding the roles and rules of a product is a business question, not a technical one, and it is one you should expect to answer when you build something.

A rule of thumb that catches most authorization bugs in the wild: every request that touches a specific record must check that this user may touch this record. Systems that check "is the user logged in?" but forget "is this their order?" allow anyone to read anyone's data by changing the number in the URL. This exact flaw has produced many of the largest data leaks of the last decade.

4.2 Passwords done right 8 min

The oldest authentication method is a shared secret: the user and the server both know the password. The obvious design, storing each user's password in the database next to their email, is also the most dangerous thing a product can do. If the database is ever stolen (and databases are stolen constantly), every password is exposed, and since people reuse passwords, so are their bank and email accounts.

The correct design stores a hash of the password instead. A hash function turns any input into a fixed-length scramble in a way that cannot be reversed. correct-horse-battery might hash to $2b$12$K9xT…. To check a login, the server hashes what the user typed and compares the two scrambles. The server never needs the original password, and a thief who steals the database gets scrambles they cannot turn back into passwords. (Details you may hear: passwords are "salted," meaning a random value is mixed in so identical passwords do not produce identical hashes, and slow algorithms such as bcrypt or argon2 are used so that guessing billions of passwords takes years.)

The lesson for a product owner is simple and non-negotiable: if a system can email you your old password, it is storing passwords wrongly. A correctly built system can only reset a password, never reveal it.

Passwords alone are weak because people choose bad ones and reuse them. Multi-factor authentication (MFA, or two-factor, 2FA) adds a second, independent proof: something you have (a code from an authenticator app or a hardware key) or something you are (a fingerprint or face) on top of something you know (the password). A stolen password alone then no longer opens the account. Every serious product should offer it, and every business should require it for staff accounts. Newer passkeys go further and replace passwords with a cryptographic key stored on your device, unlocked by fingerprint or face; they are becoming the default on major platforms.

4.3 Staying logged in: cookies, sessions, and tokens 10 min

Session 3 established that HTTP is stateless: each request arrives with no memory of the last. Yet you log in once and stay logged in for weeks. How does the server recognise you on the second request?

The mechanism is the cookie. When you log in successfully, the server's response includes an instruction: "browser, please store this piece of text and send it back to me with every future request." The browser obeys automatically. The text is usually a session ID: a long random string that means nothing by itself but which the server has recorded in its session store (the Redis box in Session 3) alongside "this is Dana, logged in at 8:14, expires in 14 days." Each request carries the cookie; the server looks up the ID; now it knows who is asking. Log out, and the server deletes the record so the ID becomes worthless.

Three consequences worth drawing out:

  • The cookie is as good as the password while it lasts. Anyone who copies the session cookie can act as Dana until it expires. This is why cookies are marked to be sent only over HTTPS and never be readable by JavaScript, and why sensitive actions (changing the password, paying) often ask for the password again.
  • This is how any web server in a load-balanced pool can serve Dana. The identity travels with the request; the facts live in the shared store. Stateless servers, from Session 3, depend on exactly this.
  • Cookies are also how advertising tracks people. The same mechanism that remembers your login lets a third-party advertising server recognise your browser across every site that shows its ads. Cookie-consent banners and privacy laws exist because of that second use, not the first.

Mobile apps and APIs often use a variant: instead of a random ID that the server looks up, the server issues a token: a signed piece of text that itself says "Dana, valid until Friday" and cannot be forged because it carries a signature only the server could produce. The most common format is the JSON Web Token (JWT, said "jot"). The client sends the token in an Authorization header rather than a cookie. The concept is identical: prove who you are once, receive a credential, present the credential thereafter.

4.4 HTTP Basic Authentication and API keys 7 min

Before cookies and tokens there was the simplest possible scheme, built into HTTP itself and still in use: HTTP Basic Authentication. When a server requires it, the browser pops up its own plain grey username/password box (you have probably seen one on a router or a staging site). The browser then attaches the credentials to every request:

GET /admin/reports HTTP/1.1
Host: www.rosenthalsbakery.com
Authorization: Basic ZGFuYTpjb3JyZWN0LWhvcnNl

That jumble after Basic is not encryption. It is Base64 encoding of the text dana:correct-horse, and anyone can decode it in a second. Basic Auth therefore has two rules and two uses:

Rules

  • Only ever over HTTPS. Over plain HTTP the password crosses the network in the clear on every request.
  • Only for things where a shared, static password is acceptable. There is no logout, no expiry, no second factor.

Where you still meet it

  • Putting a quick password in front of a staging site so the public cannot see it.
  • Internal tools and admin pages for a handful of staff.
  • Some APIs, where the "username" is an account ID and the "password" is a key. Stripe's API, for instance, accepts your secret key this way.

A close cousin is the API key, which we met in Session 2. It is a long random secret issued by a service provider that your back end presents with each call so the provider knows whose account to bill and what it may do. Keys are passwords for programs, and they must be treated as such: stored in server configuration (a file called .env is the convention), never typed into front-end code, and never committed into a Git repository. Automated bots scan GitHub around the clock for accidentally published keys and can spend thousands of dollars of someone's cloud budget within minutes. When you use Claude Code with the Claude API or any other service, this is the single most important habit to build.
