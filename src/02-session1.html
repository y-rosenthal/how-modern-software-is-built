From a File on Your Laptop to a Page on the Internet

We start with the simplest possible website, a single text file opened in a browser, and follow it all the way to being served to strangers over the internet. Along the way we meet the browser, the three languages of a web page, addresses, servers, and the request-and-response conversation that every website depends on.

By the end of this session students can

  • Explain the client–server model and identify the client and server in everyday examples.
  • Describe what HTML, CSS, and JavaScript each contribute to a web page.
  • Trace what happens between typing a web address and seeing a page, including DNS and HTTP.
  • Distinguish a static website from a dynamic one and explain the limits of static sites.
  • Say where Python runs in a web application and why it does not run in the browser.

1.1 Why architecture is a business topic 5 min

When an architect designs a building, they decide where the load-bearing walls go, how people move between floors, and where the plumbing runs. Change those decisions after the concrete is poured and the cost is enormous. Software has the same property. Architecture is the set of big structural decisions about a piece of software: what its major parts are, what each part is responsible for, and how the parts talk to each other.

Three reasons a business student should care:

  • Cost. Architecture decides whether you pay a few dollars a month or tens of thousands. It decides whether adding customers adds cost linearly or barely at all.
  • Risk. Architecture decides what happens when a component fails, how a data breach could occur, and whether the product survives a viral moment or collapses under it.
  • Speed. Architecture decides how fast a team (or you with an AI coding assistant) can add features without breaking what already works.

You will not be writing the load-bearing walls yourself in this course. But you will be talking to people and tools that do, and the person who cannot follow the conversation does not get a vote.

Instructor note

A good opener is to ask the class to name a website or app that "went down" recently and speculate why. Most outages trace back to a component in this module: a database, a server that ran out of capacity, a login system, a third-party service. Return to their examples as the relevant pieces appear.

1.2 Clients, servers, and programs 10 min

Almost every piece of modern software follows one pattern: one computer asks, another computer answers. The computer that asks is the client. The computer that answers is the server. Together this is the client–server model.

Two things students often get wrong about servers:

  • A server is an ordinary computer. It has a processor, memory, and a disk exactly like a laptop. It usually has no screen or keyboard because nobody sits at it. It lives in a building full of other servers (a data center) with reliable power, cooling, and a fast internet connection. It runs 24 hours a day, waiting.
  • "Server" also names a program. A web server is a program whose only job is to listen for requests and hand back web pages. The same physical computer can run several server programs at once. In conversation, "the server" means whichever of the two is obvious from context.
Analogy

A restaurant. You (the client) sit at a table and ask the waiter for a menu. The kitchen (the server) prepares what you ask for and sends it out. You never enter the kitchen and you don't need to know how it is organized to place an order. The menu is the agreed-upon list of what you may ask for. We will reuse this restaurant repeatedly; the menu becomes the API in Session 2.

Everyday examples students already use, with the client and server identified:

ActivityClientServer
Reading news on your phoneThe browser or news app on the phoneThe newspaper's computers that hold the articles
Sending a WhatsApp messageThe WhatsApp appMeta's messaging servers, which pass the message to your friend's phone (another client)
Checking your bank balanceThe banking appThe bank's servers holding account records
Asking Claude a questionThe Claude app or Claude Code on your computerAnthropic's servers running the AI model

The client for a website is nearly always a web browser: Chrome, Safari, Firefox, Edge. The browser is itself just a program installed on your computer. Its job is to request pages and turn what comes back into pictures and text on the screen.

1.3 A web page is three languages 15 min

Here is a surprising fact: a web page is a plain text file. You can open it in Notepad. If you save a text file with the name index.html, type a few lines into it, and double-click it, your browser will display it as a web page. No internet connection, no server, no company involved.

The text inside that file is written in up to three languages, each with a separate job.

HTML: the content and its structure

HTML (HyperText Markup Language) says what is on the page: this is a heading, this is a paragraph, this is an image, this is a link to another page. It does this with tags, labels in angle brackets that wrap the content.

<!DOCTYPE html>
<html>
  <head>
    <title>Rosenthal's Bakery</title>
  </head>
  <body>
    <h1>Rosenthal's Bakery</h1>
    <p>Fresh bread every morning since 1998.</p>
    <img src="storefront.jpg" alt="Our shop">
    <a href="menu.html">See the menu</a>
  </body>
</html>

Read it aloud and it almost explains itself: <h1> is a top-level heading, <p> is a paragraph, <img> places an image stored in a file called storefront.jpg, and <a href=...> is a link (an "anchor") to another page called menu.html. HTML alone gives you a working but ugly page: black text on white, default fonts, no layout.

CSS: how it looks

CSS (Cascading Style Sheets) says what the page looks like: colors, fonts, spacing, how things are arranged, what happens on a phone screen versus a desktop monitor. A CSS rule names the thing it applies to and lists the properties to change.

h1 {
  color: #7a3e12;
  font-family: Georgia, serif;
}
p {
  font-size: 18px;
  line-height: 1.6;
}

This says: every top-level heading is a warm brown in the Georgia font; every paragraph uses 18-pixel text with comfortable line spacing. The same HTML file with a different CSS file can look like a completely different website. That separation is deliberate: content people write the HTML, design people write the CSS, and neither steps on the other.

JavaScript: what it does

JavaScript is a real programming language, the only one that browsers can run, and it makes the page do things: react when a button is clicked, check that an email address looks valid before a form is sent, show a dropdown menu, load more posts as you scroll. Without JavaScript a page is a document. With it, a page becomes an application.

const button = document.querySelector("#order-button");
button.addEventListener("click", function () {
  alert("Thanks! Your order is on its way.");
});

In words: find the element on the page whose id is order-button; when it is clicked, show a message. Students in a Python course will notice that this looks like a programming language because it is one. The syntax differs from Python (curly braces, semicolons) but the ideas are the same: variables, functions, conditions, loops.

Common confusion

JavaScript and Java are unrelated languages that share half a name for 1990s marketing reasons. Java runs on servers and in Android apps. JavaScript runs in browsers (and, since 2009, on servers too, through a program called Node.js). When people say "JS" they mean JavaScript.

The browser's act of turning those text files into pixels is called rendering. Every browser does it slightly differently, which is why the same site can look marginally different in Safari and Chrome.

1.4 The static website on your own computer 5 min

A website made only of files like the ones above, files that are written once and sent to every visitor exactly as they are, is a static website. The word "static" means the content does not change depending on who is looking or when. A brochure site for a bakery, a personal portfolio, a documentation site, and a landing page are all naturally static.

The essential point for this session: a static website needs no server at all to work on your own computer. The browser reads the files straight off your disk. This is the zero-cost, zero-infrastructure starting point from which everything else in this module is built up.

Live demo (3 minutes)
  1. Create a folder on the desktop called bakery.
  2. Ask Claude Code: "Create a one-page static website for a bakery in this folder with an index.html, a style.css, and a small script that shows a greeting when a button is clicked."
  3. Double-click index.html. Point out the address bar: it starts with file:///, meaning "a file on this machine," not https://.
  4. Change one word in the HTML in a text editor, save, and refresh the browser to show the connection between the file and the page.

Notice the limitation, though. Only you can see this page. Your friend across town cannot type anything into their browser that reaches a file on your desktop. To share it with the world, the files have to be placed on a server that is always on and reachable by address. That is the subject of the next section.

1.5 How the internet delivers a page 20 min

Suppose the bakery's files are now sitting on a server somewhere. A customer types https://www.rosenthalsbakery.com/menu.html into their browser. In the roughly half a second before the page appears, a lot happens. We take it piece by piece.

The address: anatomy of a URL

The thing you type is a URL (Uniform Resource Locator). It has parts, and each part answers a different question.

  • The domain name is the human-friendly name a business rents (typically 10 to 20 dollars a year from a registrar such as GoDaddy, Namecheap, or Cloudflare). Owning the domain is owning the brand's address on the internet.
  • The path identifies a specific page or file on that server. For a static site the path is literally a file name. For dynamic sites (Session 2) the path is more like an instruction: /orders/1234 means "show me order number 1234".
  • The query string passes extra details, like a language or a search term. When you search Google, the words you typed appear in the query string of the results URL.

Finding the server: IP addresses and DNS

Computers on the internet do not find each other by name. Every connected machine has an IP address, a number such as 142.250.72.14, and traffic is routed by number. Nobody wants to memorize numbers, so the internet has a distributed phone book called DNS (Domain Name System). When you type a domain, your browser first asks DNS "what is the IP address of www.rosenthalsbakery.com?" and gets back a number. Only then does it know where to send the request.

When a business buys a domain and then signs up with a hosting company, "pointing the domain at the host" means editing a DNS record so that the name resolves to the host's IP address. It is one of the few technical tasks a founder often does personally, and it is where the phrase "DNS changes can take up to 48 hours to propagate" comes from: the phone book is copied to thousands of servers worldwide and they refresh on a schedule.

The conversation: HTTP requests and responses

Now the browser knows the number. It opens a connection to that server and speaks a language called HTTP (HyperText Transfer Protocol). A protocol is simply an agreed set of rules for how two computers exchange messages, the way a business letter has a conventional layout. HTTP is refreshingly readable. The browser's request looks like this:

GET /menu.html HTTP/1.1
Host: www.rosenthalsbakery.com
User-Agent: Mozilla/5.0 (Macintosh) Chrome/128.0
Accept-Language: en-US

Read it as: "GET me the thing at /menu.html. I'm looking for the site called www.rosenthalsbakery.com. I'm Chrome on a Mac, and I prefer English." The server's response is equally readable:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 5120

<!DOCTYPE html>
<html> ... the actual page ...

The first line carries a status code, a three-digit summary of how things went. A handful are worth knowing because they show up in everyday life:

CodeMeaningWhen you see it
200 OKSuccess, here is what you asked forEvery normal page load
301 Moved PermanentlyThat moved; go here insteadOld links that still work after a redesign
401 Unauthorized / 403 ForbiddenYou need to log in / you're not allowedTrying to open someone else's account page
404 Not FoundNo such pageA typo in the address, a deleted page
500 Internal Server ErrorThe server's own code crashedA bug in the site; the visitor did nothing wrong
503 Service UnavailableThe server is overloaded or down for maintenanceTicket sales opening, launch-day traffic

One page usually triggers many requests. The HTML arrives first; as the browser reads it, it discovers it also needs style.css, app.js, and storefront.jpg, and sends a separate request for each. A typical commercial home page today makes 50 to 150 requests. This is why "the number of requests" is a real performance metric and why the CDN in Session 3 matters.

HTTPS: the padlock

Plain HTTP sends everything as readable text, so anyone on the same coffee-shop Wi-Fi could read the pages you request and anything you type into them. HTTPS wraps the same conversation in encryption, so that only the browser and the server can read it. The padlock in the address bar means HTTPS is on. The server proves its identity with a certificate issued by a trusted authority; since 2015 these are free (from a non-profit called Let's Encrypt) and every serious hosting service turns them on automatically. There is no longer a business reason to run a site without HTTPS, and browsers actively warn visitors away from sites that do.

Getting the files onto a server: hosting

Hosting means renting space on someone else's always-on server and putting your files there. For a static website this is astonishingly cheap or free. Services such as GitHub Pages, Netlify, Vercel, and Cloudflare Pages will take a folder of HTML, CSS, and JavaScript and serve it to the whole world, including HTTPS and a domain of your choosing, for nothing or a few dollars a month. The workflow is: put the files in the service, point your domain's DNS at it, done.

Why is it so cheap? Because serving static files is the easiest job a computer can do. The server reads a file from disk and sends it. No thinking, no computation per visitor, nothing to remember. That simplicity is the reason static sites are fast, hard to hack, and almost impossible to overload. It is also the reason they are limited, which brings us to the next section.

Instructor note

If time allows, open the browser's developer tools (F12 or right-click, Inspect) on any real site and show the Network tab. Students can watch the list of requests grow, see the status codes, and see the HTML arrive first. This makes the diagram above concrete in about 90 seconds.

1.6 Front end, back end, and the limits of static sites 10 min

Two words you will hear in every conversation about software: front end and back end. The front end is everything that runs on the user's device and that they can see and touch: the HTML, CSS, and JavaScript we have been discussing. The back end is everything that runs on the server, out of sight: the code that decides what to send, checks who you are, records your order, charges your card.

A static website is front end only. That is precisely why it is cheap, and precisely why it cannot do certain things:

  • It cannot remember anything. If a visitor fills in a form, there is nowhere for the data to go. The server just hands out files; it does not accept and store information.
  • It cannot personalise. Every visitor gets the same menu.html. There is no "Welcome back, Dana" and no shopping cart that survives a page reload, because nothing on the server knows who Dana is.
  • It cannot keep secrets. Everything in a static site is sent to the visitor's browser, so anything in it can be read by anyone. A password, a payment key, or a private price list cannot live in front-end code. This is one of the most important security rules in this module and it will return in Session 4.
  • It cannot do work on your behalf. Sending a confirmation email, charging a credit card, or generating a PDF invoice all require a program running somewhere that is not the visitor's browser.

Every one of those needs is met by adding a back end: a program on the server that receives requests, runs logic, reads and writes stored data, and produces a response tailored to the visitor. A website with a back end is a dynamic website: its pages are generated at the moment they are requested, so they can be different for every person and every moment.

Most real products mix the two. The marketing pages of a company are static; the product behind the login button is dynamic. Knowing which parts of your product genuinely need a back end, and which can be static, is one of the first cost-saving architecture decisions a founder can make.

1.7 Where Python fits 5 min

You are learning Python in parallel with this course, so it is worth saying exactly where it fits into the picture. The browser can run only JavaScript. Python does not run in the browser. Python runs on your computer when you run a script, and it runs on servers as back-end code. When a Python program on a server answers web requests, it is the "Program" box in the diagram above.

Python is one of the most popular back-end languages in the world, used at Instagram, Spotify, Netflix, Dropbox, and nearly every AI company. In Session 2 you will see a complete, working Python web server in about ten lines. The Python skills from your other course are directly the skills of writing back ends.

LanguageWhere it runsJob
HTML, CSSBrowserContent and appearance of pages
JavaScriptBrowser (also servers via Node.js)Interactivity in the page; also a common back-end language
PythonServers and your own computerBack-end logic, data processing, AI, scripts and automation
SQLDatabase serverAsking questions of stored data (Session 2)
Swift, KotlinPhonesNative iPhone and Android apps (Session 4)

A final piece of vocabulary. A developer who works on the front end is a front-end developer; one who works on the back end is a back-end developer; one who does both is a full-stack developer. "The stack" is the list of technologies a product uses, top to bottom: the front-end framework, the back-end language, the database, the hosting. When someone asks "what's your stack?", they are asking about your architecture.

Review questions

Session 1: From a file to a page on the internet

  1. In the client–server model, which side starts every conversation, and why does that matter for how servers are designed?The client always starts. The server only waits and answers. This means a server must be always on and reachable, and it never needs to "find" its users; it just has to handle whatever arrives. It also means a server cannot push you information you did not ask for without tricks such as the browser repeatedly asking.
  2. A web page is written in up to three languages. Name each one and state in one phrase what it is responsible for.HTML describes the content and structure (headings, paragraphs, images, links). CSS controls appearance (colors, fonts, spacing, layout). JavaScript controls behaviour and interactivity (reacting to clicks, changing the page, fetching data).
  3. Why can you open a static website from a folder on your desktop with no internet connection, but your friend across town cannot see it?A static site is just files, and a browser can read files straight off the local disk (the address begins with file:///). Your friend's browser cannot reach files on your computer because your machine is not a publicly addressable, always-on server. To share it, the files must be placed on a hosted server with a domain name pointing to it.
  4. Break the URL https://shop.example.com/products/42?color=blue into its parts and say what each part tells the browser.https is the protocol (talk securely using HTTP). shop.example.com is the domain name, identifying which server to contact (shop is a subdomain of example.com). /products/42 is the path, identifying which resource on that server (product number 42). ?color=blue is the query string, an extra detail passed as a name=value pair.
  5. What does DNS do, and what everyday object is it usually compared to?DNS translates a human-readable domain name into the numeric IP address of the server hosting it. It is compared to a phone book or contacts list: you look up a name and get a number you can actually dial.
  6. A customer reports seeing "500 Internal Server Error" while another reports "404 Not Found." Which one suggests a bug in your own code, and which suggests a bad link or typo?500 means the server's own program failed while handling the request, so it points to a bug or outage on your side. 404 means the server is fine but no such page exists at that path, which usually indicates a broken link, a deleted page, or a typo in the address.
  7. Give two things a purely static website cannot do, and explain in one sentence what has to be added to do them.Any two of: remember information a visitor submits, personalise pages per visitor, keep a secret such as a payment key, or perform work such as sending emails or charging cards. To do them you add a back end: a program on the server that runs per request, applies logic, and reads and writes stored data.
  8. Your Python course teaches you to write programs. In a web application, where would that Python code run, and why not in the visitor's browser?Python runs on the server as back-end code (or on your own computer as a script). It does not run in the browser because browsers only execute JavaScript; that is the one language every browser was built to understand.
