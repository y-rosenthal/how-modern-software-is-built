"Add an order: customer 3, product 1, quantity 2, status placed." "Change order 88's status to ready." "Remove order 89." The database assigns the new order its order_id automatically. Notice how much rides on the WHERE clause: DELETE FROM orders; with no WHERE deletes every order in the company. This is not a hypothetical. It is a well-known category of career-defining mistakes, and the reason production databases have backups and restricted permissions (Session 4).

Creating the structure: CREATE TABLE

CREATE TABLE orders (
    order_id     INTEGER PRIMARY KEY,
    customer_id  INTEGER REFERENCES customers(customer_id),
    product_id   INTEGER REFERENCES products(product_id),
    quantity     INTEGER NOT NULL,
    ordered_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status       TEXT DEFAULT 'placed'
);

This defines the table itself: each column, its data type (whole number, timestamp, text), which column is the primary key, which columns are foreign keys (REFERENCES), and which are required (NOT NULL). The database will now refuse to save an order with no quantity, or one pointing at a customer who does not exist. Those constraints are business rules enforced by the storage layer, which is far more reliable than hoping every program remembers to check.

What students should take away
  • SQL is a language of questions and instructions about tables. It reads roughly like English.
  • Reading is SELECT; writing is INSERT, UPDATE, DELETE; structure is CREATE TABLE.
  • JOIN is how information split across tables is put back together.
  • They should be able to look at a query Claude Code writes and say "this deletes every row" or "this only fetches Boston customers."

3.5 Beyond tables: NoSQL and ORMs 8 min

NoSQL databases

Not all data fits neatly into fixed columns. A product catalogue where every product has different attributes (shoes have sizes, laptops have memory) fights the relational model. NoSQL databases relax the rules. The most common kind, a document database such as MongoDB, stores each record as a JSON-like document with whatever fields it needs:

{
  "product_id": 3,
  "name": "Challah",
  "price": 8.00,
  "tags": ["bread", "shabbat", "egg"],
  "sizes": {"small": 6.00, "large": 8.00}
}

Flexibility has a price: the database no longer enforces that every product has a price, and combining data across collections is clumsier than a JOIN. The choice between relational and NoSQL is a genuine architecture decision, but a simple rule of thumb serves most businesses: start relational. Business data (customers, orders, invoices, inventory) is naturally tabular and you will want the guarantees. Reach for NoSQL when you have a specific reason: extremely high write volume, genuinely irregular data, or a cache.

ORMs: letting Python speak to the database

Developers rarely type SQL into their programs directly. Most use an ORM (Object-Relational Mapper), a library that lets the program treat rows as ordinary Python objects and generates the SQL behind the scenes:

# Python with an ORM (SQLAlchemy):
boston = Customer.query.filter_by(city="Boston").all()

# ...which the ORM turns into SQL for you:
# SELECT * FROM customers WHERE city = 'Boston';

When Claude Code builds a back end for you, it will almost certainly use an ORM, and files called "models" describe the tables. The point for a business reader: the concepts (tables, keys, queries) are unchanged; the ORM is a convenience layer on top of them.

3.6 Putting it together: the three-tier architecture 10 min

We now have three distinct kinds of component, and the standard name for arranging them is the three-tier architecture:

  1. Presentation tier: the front end. HTML, CSS, and JavaScript in the browser (or the screens of a phone app). Shows things to people and collects their input.
  2. Application tier (also called the logic tier or the back end): the server program. Receives requests, enforces business rules, decides what to do, talks to the database, and returns responses. This is where business logic lives: prices, discounts, permissions, validation, workflows.
  3. Data tier: the database. Stores and retrieves the facts.

Follow one order through all three tiers. Dana clicks "Order 2 challahs":

Three observations that will matter for the rest of the module:

  • The browser never talks to the database directly. All access goes through the back end, which checks identity and applies rules. If a browser could send SQL, anyone could run DELETE FROM orders. This is why the front end can never be trusted with secrets or with enforcing rules; anything in the browser can be changed by the person using it.
  • Each tier can be changed independently. Redesign the front end without touching the database. Swap SQLite for PostgreSQL without changing the HTML. Rewrite the back end from Python to something else while the other two tiers carry on. This independence is the whole point of tiers.
  • Each tier can be placed on different hardware. Today all three might run on one laptop. Tomorrow the database can move to its own machine and the back end can be copied onto ten. That is Session 4.
Instructor note

Ask students to name the three tiers for an app they use daily. For Uber: the app on the phone (presentation), Uber's servers matching riders and drivers and computing fares (application), and the records of trips, drivers, and payments (data). Then ask where the surge-pricing rule lives. It is in the application tier, on the server, precisely so that no one can tamper with it from the app.

What is JSON, and why did it become the standard format for APIs?JSON is a text format for data: curly braces hold named values, square brackets hold lists, text is quoted, numbers and true/false stand alone. Give three reasons a business stores its data in a database rather than in ordinary files.Any three of: many users and programs can write at the same time without corrupting the data; searches over millions of records are fast thanks to indexes; transactions guarantee changes are all-or-nothing so data is never left half-saved; complex questions (reports) can be asked in one line of SQL; constraints such as "every order must have a customer" are enforced automatically.

Which term describes that column?Storing the ID avoids copying the same customer details into every order. If Dana changes her email, it is updated once in the customers table and every order automatically reflects it; copies would drift out of sync. A column that holds another table's primary key is a foreign key.
  7. In plain English, what does this query return?
    SELECT customers.name, COUNT(*) FROM orders JOIN customers ON orders.customer_id = customers.customer_id GROUP BY customers.name;For each customer who has placed at least one order, it returns the customer's name and the number of orders they have placed. The JOIN attaches the customer's name to each order via the customer_id key, and GROUP BY with COUNT tallies the orders per name.
