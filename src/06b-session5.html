5.5 OAuth: how "Sign in with Google" works 15 min

Two problems appear the moment products start working together. First, a new app wants to let users sign up without inventing yet another password, so it offers "Sign in with Google" or "Continue with Apple." Second, an app wants to use another service on the user's behalf: a scheduling tool that reads your Google Calendar, an accounting app that pulls transactions from your bank, a Claude integration that reads your Notion pages. The naive solution to both, asking the user to type their Google password into the new app, is catastrophic: the app would then hold a password that opens everything, forever, and the user could revoke it only by changing the password everywhere.

OAuth 2.0 solves both problems with one idea: the user never gives the app their password. Instead, the user is sent to the service they already trust (Google), approves a specific, limited request there, and the trusted service hands the app a special-purpose key.

Analogy

A valet key. You would not hand a valet the master key to your car, house, and safe. A valet key starts the engine, opens the driver's door, and does nothing else; you can have it cancelled without changing any other lock. OAuth issues valet keys for online accounts. The key is called an access token; the "engine only" restriction is called a scope.

The four parties

OAuth conversations always involve four roles. Learning their names makes every OAuth diagram readable.

RoleWho it isIn "Sign in with Google" for the bakery app
Resource ownerThe user, who owns the data or identityDana
ClientThe application that wants access (a different sense of "client" than in Session 2)The bakery's web app
Authorization serverThe trusted service that authenticates the user and issues tokensGoogle's login and consent system
Resource serverThe service holding the data the token unlocksGoogle's profile or Calendar API

The authorization-code flow, step by step

Walk the class through it slowly; it is the most intricate diagram in the module and worth the time.

  1. Steps 1–3. The bakery's app does not show a password box. It sends Dana's browser to Google, telling Google which app is asking (a public client ID the bakery registered with Google beforehand) and what it wants (the scopes: here just email and name).
  2. Step 4. Dana logs in at Google, with Google's password box and Google's MFA. The bakery sees none of it. Google shows a consent screen listing exactly the scopes requested. Dana can refuse.
  3. Steps 5–6. Google sends the browser back to a pre-registered address at the bakery with a one-time authorization code. The code is deliberately useless on its own: it expires in a minute and can be redeemed only by the party holding the matching secret.
  4. Steps 7–8. The bakery's back end, in a direct server-to-server call the browser never sees, presents the code together with its client secret (a password that only the bakery's server and Google know). Google returns the access token, valid for about an hour, plus a longer-lived refresh token for obtaining new ones, plus an ID token describing who Dana is.
  5. Steps 9–10. The bakery uses the access token to ask Google for Dana's email and name, matches or creates her account, and issues its own ordinary session cookie. From here on, Session 5.3 applies.

Why the roundabout design? Because of what it protects against. Dana's password is never disclosed to the bakery. The token can do only what the scopes allow, so even a badly behaved app cannot read her email if it asked only for her name. Dana can see every app she has authorised in her Google account settings and revoke any of them with one click, instantly, without changing her password. And the access token expires quickly, so a stolen one has a short life. Compare each of those properties with the "type your Google password into our app" alternative and the value of the standard becomes obvious.

Login versus access: OpenID Connect

Strictly, OAuth is about authorization: granting an app access to resources. Using it for login (proving who the user is) was such a common desire that a thin standard was added on top: OpenID Connect (OIDC). It defines the ID token in step 8 and what it must contain. Every "Sign in with Google / Apple / Microsoft / GitHub" button is OIDC over OAuth. When a vendor says they support single sign-on (SSO), they mean a company's employees can log into the vendor's product with the company's central identity provider (Google Workspace, Microsoft Entra, Okta) using OIDC or its older enterprise cousin, SAML. For a business selling software to other businesses, supporting SSO is often a condition of the sale.

Business translation
  • Offering "Sign in with Google" raises sign-up conversion and removes your password-storage liability. Most new products should offer it alongside email and password.
  • When another app asks to "connect" to your Google, Slack, or bank account, read the scopes on the consent screen. That list is the entire extent of what it can do.
  • Your own product can be the resource server: letting partners "connect to your app" via OAuth is how platforms such as Shopify and Slack built their ecosystems.

5.6 Security basics every product owner should know 7 min

You do not need to be a security engineer, but a handful of ideas will let you ask the right questions and recognise the most common mistakes, several of which have already appeared in this module.

  • Encrypt in transit and at rest. HTTPS everywhere (in transit); encrypted disks and database volumes (at rest). Every cloud provider offers the latter as a checkbox. Turn it on.
  • Never trust the front end. Anything in the browser or the app can be read and altered by the user. Prices, discounts, permissions, and secrets belong on the server. This was the lesson of the three-tier diagram in Session 3.
  • Watch for injection. The most famous web vulnerability, SQL injection, happens when text a user types is pasted straight into a SQL query. If a login form builds SELECT * FROM users WHERE name = ' + whatever was typed + ', then typing ' OR 1=1 -- makes the query true for every user. The fix (parameterised queries, where user input is passed to the database separately from the SQL) is automatic in every modern framework and ORM, which is one reason to use them. A cousin, cross-site scripting (XSS), does the same trick with HTML and JavaScript. The general rule: user input is data, never code.
  • Least privilege. Every person, program, and API key gets the minimum access it needs. The web server's database account should not be able to drop tables. An intern should not be an administrator. A leaked key that can only read is a nuisance; one that can do everything is a disaster.
  • Keep secrets out of code. Passwords, API keys, and client secrets go in environment configuration, never in source files and never in Git. Rotate any secret that has ever been exposed.
  • Keep software updated and take backups. Most breaches exploit known holes in unpatched software. Managed services (PaaS, managed databases) patch for you, which is a security argument for them, not only a convenience one. And test that backups actually restore; an untested backup is a hope, not a plan.

The industry maintains a list of the ten most common web application risks, published by an organisation called OWASP. You do not need to memorise it, but "have we reviewed against the OWASP Top Ten?" is a question that any engineer or AI coding assistant can act on, and asking it marks you as someone who knows what matters.

5.7 Beyond the browser: mobile, desktop, embedded 10 min

Everything so far has assumed the client is a browser. Most software you use is not a website, and yet almost all of it is built from the same parts. The distinction that matters is where the front end runs; the back end and the database are the same story.

This picture explains several things business people encounter:

  • Why "we need an app" is a smaller decision than it sounds. If the back end and API already exist, a mobile app is a new front end, not a new system. If they do not exist, the app project is secretly also a back-end project.
  • Why companies start with the web. A web app has no store review, no commission, instant updates, and one codebase. Native apps are added when the product needs the camera, notifications, offline use, or a home-screen presence.
  • Why the API is the product's most durable asset. Front ends are rewritten every few years as fashions and devices change; a well-designed API and its database outlive several generations of them.
  • Why embedded devices are the exception. A thermostat's software, its firmware, must still work in 2036 if the device was sold in 2026, may never be updated, and can physically harm someone if it fails. The engineering culture is correspondingly conservative, and the cost of a mistake is a recall rather than a redeploy.

5.8 Where AI fits 5 min

Since this course is about building products with AI, the last question is where a model such as Claude sits in everything above. The answer is reassuringly familiar: an AI model is a third-party API called from your back end. It is the Claude API box that has been sitting at the edge of the diagrams since Session 3.

Three practical consequences:

  • The key stays on the server. A model call from the browser would expose your API key to every visitor, who could run up your bill. All the reasoning of Section 5.4 applies.
  • Your data is the differentiator. The model is the same one your competitors can rent. What makes an AI feature yours is the context your back end adds from your database (this customer's history, your product catalogue, your policies) before calling the model. That pattern, fetching relevant data and putting it in the prompt, is what people mean by retrieval-augmented generation (RAG).
  • AI calls have cost, latency, and failure modes. A model call takes seconds and costs money per token (here a token is a fragment of a word, nothing to do with the login tokens of Section 5.3), so it is treated like any slow, paid third-party API: cached where possible, monitored, and given a fallback. When Claude Code builds an AI feature for you, these are the questions to ask it.

Step back and look at the whole module. A model such as Claude, the tool you are learning to build with, is itself served through exactly the architecture described here: a front end (the Claude app, or Claude Code in your terminal), load-balanced back ends behind an API, databases, caches, OAuth login, and an API key for programs. The next time you use it, you will know what is on the other end of the request.

Review questions

Session 5: Identity, security, and software beyond the browser

  1. Define authentication and authorization, and give an example where a system gets the first right and the second wrong.Authentication verifies who a user is (password, code, fingerprint, Google login). Authorization decides what that identified user may do. Example of getting only the first right: a site that checks you are logged in but lets you view any order by changing the number in the URL, so any customer can read any other customer's order.
  2. Why should a database store a hash of each password rather than the password itself? What does it mean if a company can email you your old password?A hash is a one-way scramble that cannot be reversed to recover the password, so if the database is stolen the attackers cannot read users' passwords (which people reuse elsewhere). Login works by hashing what the user types and comparing. If a company can send you your old password, it is storing passwords in readable form, which is a serious security failure.
  3. HTTP is stateless, yet you stay logged in. Explain the role of the cookie and the session store.On login the server creates a session record ("ID a8f3… = Dana, expires in 14 days") in a shared session store and tells the browser to save the ID in a cookie. The browser automatically sends the cookie with every later request; the server looks up the ID and knows who is asking. Any web server in the pool can do this lookup, which is what allows servers to be stateless.
  4. What does HTTP Basic Authentication send, in what form, and why is it acceptable only over HTTPS?It sends the username and password on every request in an Authorization header, encoded in Base64 (for example Base64 of "dana:correct-horse"). Base64 is encoding, not encryption, and is instantly reversible, so over plain HTTP the password would be readable by anyone on the network. HTTPS encrypts the whole exchange, which is the only thing keeping the credentials private.
  5. Name the four roles in OAuth and identify each one when a scheduling app asks to read your Google Calendar.Resource owner: you, the user who owns the calendar. Client: the scheduling app requesting access. Authorization server: Google's login and consent system, which authenticates you and issues the token. Resource server: the Google Calendar API that holds the data the token unlocks.
  6. In the OAuth flow, why does Google send a one-time code back through the browser instead of the access token itself? And why does the user never type their Google password into the bakery's app?The code is useless on its own: it expires quickly and can only be exchanged for a token by presenting the client secret, which lives on the bakery's server. Exchanging it in a server-to-server call means the token never passes through the browser where it could be intercepted or leaked. The user types their password only at Google so the bakery never possesses it; the bakery receives a scoped, expiring, revocable token instead, which limits damage if the app is careless or compromised.
  7. What is a scope in OAuth, and where does the user see it?A scope is a named, limited permission the application requests, such as "read your email address" or "read calendar events." The user sees the requested scopes on the consent screen at the authorization server (Google) before approving, and the issued token can do nothing beyond them.
  8. What is SQL injection, and why does using a modern framework or ORM largely prevent it?SQL injection occurs when text a user types is pasted directly into a SQL statement so that it runs as part of the query; typing ' OR 1=1 -- into a login form could make the query match every user. Modern frameworks and ORMs use parameterised queries, which send user input to the database separately from the SQL text so it is always treated as data, never as code.
  9. Your company has a web app with a working API. The CEO wants "an iPhone app and an Android app." In architectural terms, how big is that project, and what alternative might you propose first?Because the back end and API already exist, the apps are new front ends rather than a new system: the mobile apps call the same API and use the same data and login. It is still real work (two native codebases or one cross-platform codebase, app store review, updates). A cheaper first step is a progressive web app, which is installable to the home screen from the existing web app with no store involvement, unless the product needs native-only features such as rich offline use or certain hardware access.
  10. Where in a product's architecture does a call to an AI model such as Claude belong, and why must it not be made from the browser?In the back end (application tier), as a call to a third-party API, after the back end has checked who is asking and gathered relevant data from the database to include in the prompt. It must not be made from the browser because the API key would then be visible to every visitor, who could use it to run up the company's bill, and because the business rules and private data added to the prompt must stay on the server.
